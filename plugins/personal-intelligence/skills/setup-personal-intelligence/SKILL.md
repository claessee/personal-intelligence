# Set up Personal Intelligence

Build a private, inspectable map to the user's existing information. Explicit user instructions control this workflow. Use existing tools; setup does not authorize installing integrations, changing permissions, scanning personal collections, publishing or acting on example questions. Do not delegate unless the user authorizes it.

1. Read relevant workspace instructions and any existing source map first. Ask for a private configuration location only if none is supplied by the user or workspace. Never broadly search the home directory. Use the templates in `assets/` and read [the schema](references/profile-schema.md) when creating or checking configuration.
2. Capture the user's complete original inputs in an independent `requirements.json` before implementing them: chosen domains, subjects, named source roles, required capabilities and priority labels. Use known setup records only within authorized scope; distinguish recovered original inputs, current confirmations and missing evidence. Do not invent priorities or ask the user to reconstruct discoverable inputs one at a time. No user data belongs in the skill/package or a public repository.
3. Resolve genuine authority/privacy choices with focused questions. Prefer narrow metadata checks for technical uncertainty. Keep patients, household, organization, owner-private, professional and project scopes separate. A folder or label does not grant access to everything inside it. An explicit finance question is required before financial retrieval; onboarding may record financial routing metadata without opening financial records.
4. Identify desired capabilities and existing working routes before recommending dependencies. For missing basic macOS Calendar, Reminders, Contacts, Maps and Weather, recommend iMCP as the starting integration and read [the integration guide](references/integration-guide.md). Enable only the user's chosen capabilities and explain permission/dependency limits. cal-cli and RemCTL are optional advanced alternatives; do not offer an unverified public installation link. Gmail and MoneyWiz remain separate optional integrations. Package installation connects no accounts or integrations; existing authorized file readers need no additional MCP. Follow [installation and onboarding](references/installation.md) for client/package guidance. Preserve all private routing choices.
5. Implement each confirmed requirement in private `profile.json` and resolve exact existing locations/instruction references in `local-map.json`. Preserve working integrations and existing source locations. Separate source authority, provider readiness, permission and freshness. Record missing capabilities and dependencies as unavailable/unverified rather than installing a replacement. Distinguish configured metadata, observed tool catalog, permission state and a dated successful scoped read; none establishes a successful write. Query access to existing provider schemas only when authorized; email access stays within the designated connected provider.
6. Compute the requirement digest with `scripts/profile_tools.py fingerprint --requirements <private-file>` and set `requirements_sha256` in the profile. Run `validate` with the three private metadata files. It checks completeness, subject bindings, gates and safe structure, not tool liveness, content truth or a permission system. Do not derive the requirement baseline from the routes it is supposed to check. A changed baseline requires user-backed reconciliation; a digest is not proof of authorization.
7. Test useful ordinary questions only when supplied/authorized and safely scoped. Use the recipient's actual sources through existing tools, one patient/topic/project/trip at a time. Select a small acceptance target suited to their domains; do not impose a fixed large checklist. Record factual accuracy, source identity/date/role, limitations, coverage and elapsed time when available. Keep private transcripts/results outside Git. Distinguish offline checks, user-confirmed passes and independently inspected answer/source evidence.

Before replacing a private configuration file, preserve `<stem>_prev.<ext>`, retaining any prior backup under a distinct dated name. Use restrictive local modes for private metadata where supported. Report implemented requirements, remaining ambiguity, actual source/tool limitations and acceptance status. Instruction edits or registration alone cannot establish a passing answer.

Use [the synthetic exercise](references/synthetic-exercise.md) only for an expressly requested offline demonstration. It is not a user profile or permission to read personal sources.
